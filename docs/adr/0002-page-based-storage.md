# ADR-002: ページベースのストレージ管理を採用する

## Status

Accepted

## Context

RDBでは、レコードを永続ストレージへどのような単位で読み書きするかを決める必要がある。

本プロジェクトはブラウザ内で動作する軽量RDBを目標としており、主な永続化先としてOPFSを想定している。

単純な実装としては、テーブル全体やレコード単位でデータを読み書きする方法も考えられる。

しかし将来的に以下を実装する場合、ストレージ上の固定された管理単位が必要になる。

* B+Tree
* インデックス
* ページキャッシュ
* 部分的な読み書き
* トランザクション
* WAL
* 空き領域管理
* クラッシュリカバリ

そのため、RDB内部の基本的なストレージ単位を明確に定義する必要がある。

## Decision

永続ストレージを固定長の**ページ**に分割し、ページ単位で管理する。

概念的には以下の構造とする。

```text
Database
  │
  ▼
Page Manager
  │
  ├─ Page 0
  ├─ Page 1
  ├─ Page 2
  └─ ...
        │
        ▼
     Storage
        │
        ├─ Memory
        └─ OPFS
```

DBの上位層はOPFSなどの物理ストレージへ直接アクセスせず、Page Managerを介してページを読み書きする。

基本的なAPIは以下のような形を想定する。

```rust
type PageId = u32;

trait Storage {
    fn read_page(&self, page_id: PageId, buf: &mut [u8])
        -> Result<()>;

    fn write_page(&mut self, page_id: PageId, buf: &[u8])
        -> Result<()>;
}
```

Page Managerは以下を担当する。

* PageIdとストレージ上の位置の対応
* ページの読み込み
* ページの書き込み
* 新規ページの確保
* 空きページの管理

ページ内部のレコード形式やB+Treeノード形式については別ADRで決定する。

## Page Size

初期実装では固定長ページを採用する。

具体的なページサイズは実装・計測を通じて決定するため、本ADRでは固定しない。

候補として以下を想定する。

* 4 KiB
* 8 KiB
* 16 KiB

ブラウザ・OPFS環境での読み書き性能、WASMメモリ使用量、レコード格納効率を測定して決定する。

ページサイズの決定は別ADRとする。

## Why Pages

### 部分的なI/Oが可能になる

DB全体を読み書きする必要がなく、必要なページだけを取得できる。

### インデックスと相性がよい

B+Treeの各ノードをページに対応させることで、ストレージとの対応関係を単純にできる。

### キャッシュを導入できる

頻繁に利用するページだけをWASMメモリ上へ保持できる。

```text
Query
  ↓
Page Manager
  ↓
Page Cache
  ├─ Hit  → WASM Memory
  └─ Miss → OPFS
```

### トランザクション実装へ発展させやすい

変更単位をページとして管理できるため、将来的なWALやクラッシュリカバリにつなげやすい。

## Alternatives

### レコード単位で保存する

実装は単純になる。

一方、レコード数が増えた場合のI/O回数が増えやすく、B+Treeやページキャッシュとの統合も難しくなるため採用しない。

### テーブル単位で保存する

非常に小規模なDBでは単純な設計になる。

しかし一部のレコード変更でもテーブル全体の読み書きが必要になりやすく、データ量の増加に弱いため採用しない。

### IndexedDBのオブジェクト単位をそのまま利用する

ブラウザ標準の永続化機構を利用できる。

しかしDB内部の物理構造がIndexedDBへ強く依存し、ページ管理・B+Tree・WALなどを自ら実装するという目的から外れるため採用しない。

## Consequences

### Positive

* B+Treeなどのストレージ構造を実装しやすい
* 必要な部分だけ読み書きできる
* ページキャッシュを導入できる
* ストレージ実装をOPFSから分離できる
* WALやクラッシュリカバリへ発展させやすい
* 一般的なRDBMSのストレージ構造を学習できる

### Negative

* レコードを単純に保存する場合より実装が複雑になる
* ページ内の空き領域管理が必要になる
* 可変長レコードへの対応が必要になる
* ページサイズという追加の設計判断が発生する
* ページ分割やページ統合などの処理が必要になる

## Initial Implementation

初期段階では以下だけを実装する。

```text
Storage
   ↓
Page Manager
   ↓
固定長 Page
```

まずMemoryStorageを使用してページ管理をテストする。

その後OPFSを利用するStorage実装を追加する。

B+Tree、レコード配置、ページキャッシュ、WALなどはPage Managerの上に段階的に構築する。

## Non-goals

このADRでは以下を決定しない。

* ページサイズ
* ページ内部のレイアウト
* レコードフォーマット
* B+Treeの構造
* ページキャッシュ方式
* WAL方式
* MVCC方式

これらは独立した設計判断として別ADRで扱う。
